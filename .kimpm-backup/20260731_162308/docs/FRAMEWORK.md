# KimPM Framework v1.0

## 1. 목적

KimPM Framework는 아이디어부터 운영까지 모든 개발 프로젝트를 동일한 기준과 절차로 관리하기 위한 표준 개발 프레임워크다.

이 프레임워크의 목표는 다음과 같다.

* 프로젝트의 중심 목표를 잃지 않는다.
* 기존 기능을 보호하면서 기능을 확장한다.
* AI 개발 도구의 추측과 과도한 수정을 통제한다.
* 요구사항, 설계, 개발, 테스트, 배포 이력을 연결한다.
* 프로젝트가 중단되더라도 빠르게 다시 시작할 수 있게 한다.
* 프로젝트별 개발 품질 편차를 최소화한다.

---

# 2. 기본 운영 원칙

모든 프로젝트는 다음 원칙을 따른다.

1. 기존 기능을 절대 깨지 않는다.
2. 현재 상태를 확인하지 않고 수정하지 않는다.
3. 추측보다 실제 소스와 DB 구조를 우선한다.
4. 한 번에 하나의 명확한 작업만 수행한다.
5. 변경 전 영향 범위를 확인한다.
6. 개발 후 반드시 검증한다.
7. 작업 결과와 다음 단계를 기록한다.

---

# 3. 전체 개발 프로세스

KimPM Framework는 다음 14단계로 운영한다.

```text

13. 배포 및 운영 확인
14. 개발 이력과 다음 단계 기록
```

# 4. 단계별 실행 기준

## 01. 프로젝트 정의

프로젝트의 존재 이유와 최종 목표를 정의한다.

필수 항목:

* 프로젝트명
* 서비스 목적
* 주요 사용자
* 해결하려는 문제
* 핵심 기능
* 제외 범위
* 향후 확장 방향

완료 조건:

* 프로젝트를 한 문장으로 설명할 수 있다.
* 주요 사용자와 핵심 가치가 명확하다.
* 현재 개발 범위와 나중에 할 범위가 구분되어 있다.

---

## 02. 현재 상태 분석

신규 개발이 아니라면 반드시 기존 프로젝트 상태부터 분석한다.

확인 항목:

* 프로젝트 폴더 구조
* 사용 기술
* 현재 브랜치
* Git 변경 상태
* 구현 완료 기능
* 미완료 기능
* 오류 발생 기능
* DB 연결 상태
* 환경변수 구성
* 배포 상태

완료 조건:

* 현재 개발률을 설명할 수 있다.
* 완료, 진행 중, 미착수 기능이 구분되어 있다.
* 다음 작업의 시작 위치가 명확하다.

---

## 03. 요구사항 확정

사용자의 아이디어를 실제 개발 가능한 요구사항으로 변경한다.

요구사항은 다음 기준으로 구분한다.

* 필수 기능
* 선택 기능
* 향후 기능
* 제외 기능
* 운영 요구사항
* 보안 요구사항
* 성능 요구사항

요구사항 작성 기준:

* 기능은 사용자 행동 중심으로 작성한다.
* 모호한 표현을 사용하지 않는다.
* 완료 여부를 판단할 수 있어야 한다.
* 한 요구사항에는 하나의 목적만 포함한다.

예시:

```text
잘못된 요구사항:
사용자 기능을 편리하게 만든다.

올바른 요구사항:
사용자는 현재 위치를 기준으로 반경 1km 이내 매장을 조회할 수 있다.
```

## 04. 아키텍처 확인

개발 전 전체 시스템 구조를 확인한다.

확인 항목:

* Frontend
* Backend
* Database
* Authentication
* External API
* File Storage
* Deployment
* Monitoring
* Logging

기본 원칙:

* 기존 아키텍처를 이유 없이 변경하지 않는다.
* 기능 하나를 위해 전체 구조를 재설계하지 않는다.
* 클라이언트와 서버의 책임을 명확히 분리한다.
* 비밀정보는 클라이언트 코드에 포함하지 않는다.

완료 조건:

* 데이터 흐름을 설명할 수 있다.
* 수정 대상 계층을 구분할 수 있다.
* 신규 기능이 기존 구조에 어떻게 들어가는지 확인됐다.

## 05. 데이터베이스 설계

DB가 필요한 기능은 화면보다 먼저 데이터 구조를 확인한다.

확인 순서:

```text
업무 개념
→ 엔터티
→ 테이블
→ 컬럼
→ 데이터 타입
→ PK
→ FK
→ 제약조건
→ 인덱스
→ 샘플 데이터
```

KimPM DB 표준:

* 코드: `*_cd`
* 명칭: `*_nm`
* 일자/일시: `*_dt`
* 순번: `*_seq`
* 번호: `*_no`
* 설명: `*_desc`
* 건수: `*_cnt`
* 여부: `*_yn`

기본 원칙:

* 운영 데이터와 코드 데이터를 구분한다.
* PK와 FK를 명확히 설정한다.
* 문자열로 처리할 필요가 없는 값은 적절한 데이터 타입을 사용한다.
* 비밀번호와 인증정보는 평문 저장하지 않는다.
* 스키마 변경 전 기존 데이터 영향을 확인한다.

완료 조건:

* 테이블 생성 스크립트가 존재한다.
* 샘플 데이터 또는 Seed가 존재한다.
* CRUD 가능 여부가 확인됐다.

## 06. UI/UX 및 화면 흐름 설계

화면은 기능을 배치하는 것이 아니라 사용자의 행동 흐름을 설계하는 단계다.

확인 항목:

* 사용자 진입점
* 주요 화면
* 화면 간 이동
* 입력 항목
* 조회 항목
* 버튼 동작
* 빈 화면
* 로딩 화면
* 오류 화면
* 모바일 대응

화면 설계 원칙:

* 핵심 행동은 눈에 잘 보여야 한다.
* 한 화면에 너무 많은 기능을 넣지 않는다.
* 버튼 이름은 결과를 예측할 수 있어야 한다.
* 사용자가 현재 위치를 알 수 있어야 한다.
* 오류 발생 시 다음 행동을 안내해야 한다.

완료 조건:

* 주요 사용자 시나리오가 화면 흐름으로 연결된다.
* 화면별 입력과 출력이 정의됐다.
* 예외 상황 화면이 정의됐다.

## 07. 개발 계획 수립

개발은 기능을 작은 단위로 나누어 순서대로 진행한다.

작업 분해 기준:

```text
하나의 작업
= 하나의 목적
= 확인 가능한 결과
= 제한된 수정 범위
```

개발 우선순위:

1. 핵심 기능
2. 핵심 기능을 위한 DB와 API
3. 주요 화면
4. 예외 처리
5. 사용자 편의 기능
6. 디자인 개선
7. 운영 기능
8. 확장 기능

각 작업에는 다음 항목이 있어야 한다.

* 작업 목적
* 수정 대상
* 변경 내용
* 영향 범위
* 테스트 방법
* 완료 조건
* 롤백 방법

---

## 08. 기능 단위 개발

개발은 한 번에 하나의 작업만 수행한다.

개발 전 확인:

* 현재 Git 상태
* 수정 대상 파일
* 관련 기존 기능
* DB 구조
* 환경변수
* 기존 테스트

개발 중 원칙:

* 요청받지 않은 기능을 추가하지 않는다.
* 관련 없는 파일을 수정하지 않는다.
* 대규모 리팩터링을 동시에 하지 않는다.
* 기존 함수와 컴포넌트를 먼저 재사용한다.
* 임시 하드코딩을 최소화한다.
* 에러 처리를 생략하지 않는다.

개발 후 확인:

* 수정 파일 목록
* 주요 변경 내용
* 실행 결과
* 오류 여부
* 기존 기능 영향
* 남은 작업

## 09. 자체 검토

개발한 AI 또는 개발자는 작업 완료 후 스스로 결과를 검토한다.

필수 검토 항목:

* 요구사항이 모두 반영됐는가
* 기존 기능이 유지되는가
* 불필요한 수정이 포함되지 않았는가
* 중복 코드가 생기지 않았는가
* 예외 처리가 되어 있는가
* 보안 문제가 없는가
* 하드코딩된 비밀정보가 없는가
* 타입 오류 가능성이 없는가
* 로그에 민감정보가 출력되지 않는가

자체 검토 결과는 다음 형식으로 기록한다.

```text
검토 결과:
- 요구사항 반영: 완료
- 기존 기능 영향: 없음
- 보안 문제: 없음
- 미해결 사항: 없음
```

## 10. 테스트

테스트는 신규 기능뿐 아니라 관련 기존 기능까지 포함한다.

테스트 구분:

* 정상 흐름
* 입력값 누락
* 잘못된 입력
* 데이터 없음
* 권한 없음
* 네트워크 실패
* DB 실패
* 중복 요청
* 모바일 화면
* 기존 기능 회귀

테스트 기본 원칙:

* 성공 화면만 확인하고 완료 처리하지 않는다.
* 오류 상황을 최소 한 번 이상 확인한다.
* 기존 핵심 기능을 다시 확인한다.
* 테스트하지 못한 항목은 명확히 기록한다.

완료 조건:

* 정상 시나리오가 작동한다.
* 주요 오류가 처리된다.
* 기존 기능이 정상이다.
* 미검증 항목이 기록되어 있다.

* README
* KIMPM

* DB Standard
* Coding Standard
* Quality Standard
* Decision Log
* API 명세
* 화면 설계
* 설치 및 실행 방법

원칙:

* 실제 코드와 다른 문서를 남기지 않는다.
* 완료되지 않은 기능을 완료로 표시하지 않는다.
* 임시 결정은 임시라고 표시한다.
* 중요한 기술 결정은 Decision Log에 기록한다.

## 12. Git 형상관리

기능 단위 작업이 끝나면 Git 상태를 정리한다.

기본 순서:

```bash
git status
git add -A
git commit -m "작업 내용"
git push origin 브랜치명
```

커밋 원칙:

* 하나의 커밋에는 하나의 목적을 담는다.
* 의미 없는 메시지를 사용하지 않는다.
* 실행되지 않는 상태로 커밋하지 않는다.
* 환경변수와 비밀정보를 커밋하지 않는다.
* 대용량 임시파일을 커밋하지 않는다.

커밋 메시지 예시:

```text
feat: 프로젝트 Git 상태 조회 기능 추가
fix: 사용자 저장 시 null 오류 수정
docs: KimPM Framework 문서 추가
refactor: 프로젝트 조회 서비스 구조 정리
```

# 5. 프로젝트 진행 상태 기준

프로젝트 상태는 다음 기준으로 관리한다.

## 계획

요구사항과 개발 범위를 정의하는 단계

## 설계

아키텍처, DB, 화면, 개발 순서를 설계하는 단계

## 개발

기능을 실제 구현하는 단계

## 검토

소스 검토와 자체 검증을 진행하는 단계

## 테스트

정상, 오류, 회귀 테스트를 수행하는 단계

## 배포

운영 환경에 반영하는 단계

## 운영

배포된 기능을 점검하고 개선하는 단계

## 보류

의도적으로 개발을 중단한 상태

## 완료

정의된 개발 범위와 검증이 끝난 상태

# 6. 작업 완료 판정 기준

다음 조건을 만족해야 하나의 작업이 완료된 것으로 판단한다.

* 요청사항이 구현됐다.
* 수정 범위가 설명됐다.
* 기존 기능 영향이 확인됐다.
* 테스트 결과가 존재한다.
* 오류와 미해결 사항이 기록됐다.
* 관련 문서가 현행화됐다.
* Git 상태가 정리됐다.
* 다음 단계가 정의됐다.

단순히 소스를 수정했다는 이유만으로 완료 처리하지 않는다.

---

# 7. KimPM 표준 작업 보고 형식

모든 Codex 작업 결과는 다음 형식을 사용한다.

```text
1. 작업 목적

2. 작업 전 분석

3. 수정 파일

4. 주요 변경 내용

5. 기존 기능 영향

6. 테스트 결과

7. 발견된 문제

8. 미완료 항목

9. Git 상태

10. 다음 권장 작업
```

---

# 8. 금지사항

다음 행동은 금지한다.

* 기존 분석 없이 전체 파일 재작성
* 요청하지 않은 기능 임의 추가
* 기존 기능을 제거하고 새 기능으로 대체
* DB 구조를 확인하지 않고 컬럼 추측
* 환경변수와 비밀번호를 코드에 직접 작성
* 테스트 없이 완료 보고
* 오류를 숨기거나 성공한 것처럼 보고
* 관련 없는 대규모 리팩터링
* 여러 기능을 한 번에 구현
* Git 상태를 확인하지 않고 작업
* 실제 실행 여부를 확인하지 않고 정상이라고 판단

---

# 9. 핵심 문장

> KimPM Framework는 빠르게 많이 만드는 개발 방식이 아니라, 기존 기능을 보호하면서 확인 가능한 작은 결과를 지속적으로 쌓는 개발 방식이다.
